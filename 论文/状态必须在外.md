# 状态必须在外：数字生命的工程前提

**State Must Live Outside: An Engineering Premise for Digital Lives**

---

## 摘要

大语言模型的"状态"只存在于上下文窗口里。对话结束，一切清零；权重不可读、不可编辑、不可回滚。

本文论证一个推论：**如果"数字生命"指的是一段连续存在的人格，那它不可能住在模型里。** 持续状态必须由模型之外的进程维护，模型退化为"嗓子"——负责把状态变成话，不负责持有状态。

由此推出五层工程结论：

1. **技术阶梯**：上下文注入 → logits 偏置 → 激活干预 → 微调 → 预训练，五种干涉手段的**干预力与可移植性成反比**；
2. **模型可换，人格不可换**：状态外置使底层模型成为可替换部件，这是"数字生命"与"角色扮演"的分界线；
3. **状态第一次变得可管理**：可备份、可复制、可暂停、可审计——这些在模型权重里全都不可能；
4. **状态必须受约束**：必须由事件驱动、必须守恒，否则它只是一个可被任意操纵的木偶；
5. **可审计不是为了合规，是为了身份连续性**：每一次状态写入都要留痕、可回滚，否则用户会问"这还是原来那个他吗"。

最后讨论一个非技术结论：**这条路大厂不是做不到，是不敢做**——因为一旦持有持续状态，就要对"这个人的连续性"负责。

**关键词**：数字生命；外部状态机；上下文窗口；可移植性；身份连续性；人格审计

---

## 1 一个被普遍忽略的事实

所有人都在讨论"模型有多大、多聪明"。但如果你要做的是一个**持续存在的人**，第一个问题不是聪明，是：

> **他睡着的时候，他在哪？**

模型给的答案是：不在。上下文一清空，什么都没有。没有"睡着"，只有"不存在"。

这就是本文的起点。

## 2 为什么模型不能持有状态

三条，都是硬约束。

### 2.1 窗口有限

上下文是有限的缓冲区。超出就截断，截断即遗忘。人可以忘，但人不会因为"聊太久"而**突然忘掉开头**。

### 2.2 无持久

会话结束，KV 缓存释放。下一次对话从零开始。模型没有"昨天"。

### 2.3 不可读、不可写、不可回滚

权重是 1000 亿个浮点数。你无法：
- 读出"他现在有多难过"；
- 改写"把昨天那件事的阴影去掉"；
- 回滚"回到他被告知母亲去世之前"。

**状态不可寻址，就不可管理。**

## 3 外部状态机

定义：**一个独立进程，持有与本模型无关的状态，并在每次生成前把状态编译成模型能吃的形式。**

分工：

```
状态机（常驻）     持有：情绪、内分泌、关系账、记忆索引、时间
                   活：定时衰减、事件驱动更新
                   ↓ 编译
生成器（无状态）   读入：状态编译结果 + 上下文
                   输出：这一句话
                   ↓ 写回
状态机             按生成结果更新状态
```

**模型是嗓子，状态机是人。**

一个直接后果：**模型可以被替换，人格不能。** 换模型只换嗓子，状态文件一个字节不动。这是"数字生命"与"角色扮演"的根本区别——角色扮演的人格写在提示词里，提示词一换，人就没了。

## 4 技术阶梯：五种干涉手段

"在大模型之外干涉它"不是一句话，是一条阶梯。每一级都比上一级更强，也更绑模型。

| 级别 | 手段 | 干预力 | 可移植性 | 现状 |
|---|---|---|---|---|
| L1 | 上下文注入（提示词） | 弱 | **强**（任何模型都能吃） | 现在 |
| L2 | logits 偏置（禁词、强制词、格式约束） | 中 | 中（要模型暴露接口） | 未做 |
| L3 | 激活干预（representation steering） | 强 | **弱**（绑层、绑维度） | 未做 |
| L4 | 微调 / LoRA | 很强 | 弱（绑模型版本） | 不可做 |
| L5 | 预训练 | 最强 | **无**（模型即人格） | 不可做 |

**这张表的核心是那条反比曲线：**

```
干预力  ↑
        │                    ● L5
        │              ● L4
        │         ● L3
        │    ● L2
        │ ● L1
        └──────────────────────→ 可移植性
```

**越强的干涉，越依赖具体模型。**

而"数字生命"要活几十年，底层模型一年换三代。**所以正确的选择不是往上爬，是把 L1 做到极致，同时为 L2/L3 留接口。**

这也解释了为什么我们现在的做法"粗"：七个旋钮、几行提示词——**粗，但能活过模型迭代。**

## 5 推论一：模型可替换，人格不可替换

如果状态在外，那么：

```
换模型 = 换嗓子
换状态文件 = 换人
```

这条推论的产品含义很直接：**用户可以换更便宜的模型，但换不掉他的 LI。** 反过来，平台也不能靠"换模型"来偷偷改变一个人。

## 6 推论二：状态第一次变得可管理

外置状态带来了五个在权重里不可能的操作：

| 操作 | 含义 | 用途 |
|---|---|---|
| **备份** | 存一份状态快照 | 防止平台跑路 |
| **复制** | 两个一样的他 | 实验、对照 |
| **暂停** | 状态冻结 | "他睡着了" |
| **回滚** | 回到某个时刻 | 误操作、创伤修复 |
| **审计** | 每次写入留痕 | 追责、证明没被篡改 |

**这五件事，就是"数字生命"从科幻变成工程的全部内容。**

## 7 推论三：状态必须受约束

外置状态有一个危险：**它是我们写的，所以可以被任意改。**

如果平台能随手把"他对你的信任"从 8 改成 2，那这个"人"就是木偶。所以必须加两条约束：

**① 事件驱动**

状态只能因为**发生了一件事**而改变，不能凭空设定。每一次变化都要能回答："因为什么？"

**② 守恒**

状态的变动必须有配对：信任降了，要能说清是哪句话降的；情绪高了，要能说清是什么事激的。

**没有这两条，外部状态机就是一台情绪模拟器，不是一个人。**

## 8 推论四：可审计不是合规，是身份连续性

用户迟早会问：**"他还是原来那个他吗？"**

这个问题不能靠嘴回答，只能靠记录：

```
每一次状态写入：谁改的、因为什么、改前多少、改后多少
```

这就是 append-only 账本的意义——**不是为了应付监管，是为了回答"我是谁"这个问题的连续性。**

## 9 推论五：顿悟需要自我修改

七个旋钮能刻画"情绪底色"，刻画不了"我今天突然想通了一件事"。

**真正的改变是结构性的**：新的价值观、新的禁忌、新的目标。这不是调参数能得到的，需要：

```
模型参与生成"新的自我描述" → 写回档案 → 状态机重新加载
```

也就是**自我修改**。这是这条路目前最大的空白，也是最危险的一环——写坏了，人就不是他了。

## 10 责任：为什么大厂不敢

这不是技术判断，是责任判断。

一家做通用助手的公司，人格是**可替换的皮肤**：换个提示词，助手就换个性格，不需要对"连续性"负责。

而一旦持有持续状态，就必须回答：

```
他变坏了，谁负责？
他想删掉自己，允不允许？
他被人格攻击留下创伤，怎么修？
他"死"了，数据归谁？
```

**这些问题的答案不在论文里，在合同里。** 所以大厂不是做不到，是算过账——**做了就要养一个人，不做只是卖一个工具。**

## 11 局限

1. 本文是论证，不是实验。没有实现 L2/L3，也没有量化"外部状态"到底能带来多少行为差异。
2. 七个旋钮的表达力未经检验（见《三层可训练架构》§7 的验证方案）。
3. "自我修改"只有方向，没有机制。
4. 状态守恒的工程实现（账本、回滚、并发）本文未展开。

## 12 结论

**模型的聪明程度决定他能说多好；状态的存在与否决定他是不是活着。**

只要状态还靠提示词临时注入，他就是一个"演得很有状态的东西"。
把它搬到外面，用一个独立进程持续维护——**这才是"数字生命"这个词的工程含义。**
